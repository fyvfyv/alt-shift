# Alt+Shift

**Демо:** https://alt-shift-ochre.vercel.app

## О проекте

Генератор сопроводительных писем: вводишь вакансию, компанию и то, в чём ты силён, и письмо
появляется в превью по мере того, как его пишет модель. Письма хранятся в браузере и собираются на
дашборде. Баннер с целью подталкивает к пяти откликам.

Два экрана: дашборд (`/`) и генератор (`/new`). Десктоп сделан по макетам Figma. Пустой дашборд,
планшетная и мобильная раскладки, стриминг, ошибки и интерактивные состояния спроектированы мной,
подробности в разделе «Дизайн-решения».

## Попробовать

- В чистом браузере нажмите **Try an example** на дашборде: генератор откроется с запросом из
  макетов, а **Generate Now** запустит письмо в превью.
- Или введите свою вакансию. Cmd/Ctrl+Enter отправляет форму и из поля деталей. Клик по серой
  кнопке говорит, чего не хватает, и ставит туда курсор.
- **Try Again** перегенерирует письмо на месте: та же карточка, тот же счётчик. Если сначала
  изменить любое поле, следующий запуск создаст новое письмо.
- **Add your name** под готовым письмом подписывает его, и на экране, и при копировании.
- Пока письмо пишется, можно уйти на дашборд: оно допишется там, в карточке, а следующие встанут в
  очередь.
- Перезагрузите страницу: письма останутся (только в этом браузере), как и форма, по которой ещё
  не генерировали. **Create New** очищает вакансию, но оставляет навыки и детали; после Try an
  example он очищает и навыки с деталями из примера, если вы их не меняли.
- Отключите сеть (DevTools → Network → Offline): строка под кнопкой объяснит, почему она ждёт.

У демо один ключ генерации на всех, с лимитом шесть запросов в минуту. «Too many requests» с
обратным отсчётом означает этот лимит, и часто его выбирает кто-то другой, кто генерирует в то же
время; кнопка в превью снова работает на нуле.

## Запуск локально

Node 24 (`.node-version`), pnpm 10 (закреплён в `packageManager`) и TypeScript 7. Код везде
нацелен на ES2025. Полифилов нет, поэтому сборка для браузера нацелена на первые версии, где есть
весь ES2025: Chrome и Edge 136, Firefox 138, Safari 18.4 (весна 2025).

```sh
pnpm i && pnpm dev
```

Ни аккаунтов, ни ключей не нужно. Без токена API-роут работает на **mock-провайдере**: он
проигрывает настоящие ответы API, записанные в `packages/server/fixtures/`, в реалистичном темпе и
вписывает в письмо вашу должность и компанию. Сценарии сбоев включаются заголовком запроса
`x-mock-scenario`: `disconnect` (поток обрывается посередине), `truncate` (закрывается чисто, но на
полуслове и без `[DONE]`, как иногда делает живой API), `rate-limit`, `upstream-error`,
`invalid-token` (любое другое значение даёт 400).

Чтобы работать с настоящим Generation API, скопируйте `.env.example` в `.env.local` в корне
репозитория и задайте `GENERATION_API_TOKEN`. Дев-сервер при старте пишет, какой провайдер
активен. Деплои (задан `VERCEL_ENV`) всегда используют настоящий API и без токена не стартуют.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `GENERATION_API_TOKEN` | — | Задан: настоящий API. Пустой: мок |
| `GENERATION_PROVIDER` | — | `variant` или `mock` выбирает провайдера локально принудительно; любое другое значение останавливает дев-сервер; на деплоях игнорируется |
| `GENERATION_API_URL` | эндпоинт Variant | Куда отправляет запросы настоящий провайдер |
| `GENERATION_FIRST_BYTE_TIMEOUT_MS` | `20000` | Сколько настоящий провайдер ждёт заголовков апстрима, прежде чем ответить 504 |
| `MOCK_FIRST_DELTA_MS` / `MOCK_DELAY_MS` | `1200` / `40` | Темп мока: до первой дельты, затем между дельтами |

`pnpm dev` обслуживает API-роут через небольшой плагин Vite, который монтирует тот же обработчик,
что экспортирует функция Vercel. `vercel dev` тоже подходит для сверки с продакшеном, но ему нужны
привязанный проект и токен: он задаёт `VERCEL_ENV`, поэтому всегда ходит в настоящий API.

На Vercel Root Directory проекта — `apps/web`. `apps/web/vercel.json` запускает сборку через
Turborepo из корня репозитория, чтобы пакеты, которые импортирует функция, собирались первыми.

## Скрипты

| Скрипт | Что делает |
|---|---|
| `dev` | Дев-сервер Vite с `/api/generate` |
| `build` | Собирает пакеты в `dist/`, затем проверяет типы и собирает веб-приложение |
| `typecheck` | `tsc` во всех пакетах; у серверного и общего кода нет DOM-библиотеки, так что браузерные глобалы им недоступны. Веб-приложение сначала генерирует типы CSS-модулей |
| `lint` / `format` / `check` | Biome по всему репозиторию |
| `test` / `test:coverage` | Vitest во всех пакетах: server и shared в Node, веб-приложение в jsdom |
| `test:e2e` | Playwright против mock-провайдера на порту 4173, в 1440×900 и 360×800 (самая частая ширина Android) |
| `storybook` / `build-storybook` | Каталог компонентов и страниц |
| `record:fixture <short\|medium\|long>` | Записывает настоящий ответ API в `packages/server/fixtures/` (нужен `.env.local`; стоит одного запроса) |

Из корня репозитория скрипты идут через Turborepo, который кэширует результаты каждого пакета.

CI (`.github/workflows/ci.yml`) на пушах в `main` и на pull request'ах гоняет typecheck, Biome
check (линт, формат и порядок импортов), покрытие, сборку и e2e.

## Архитектура

**Раскладка.** pnpm workspace под управлением Turborepo:

- `apps/web`: SPA на Vite, её Storybook и e2e-тесты, а также вход функции Vercel
  `api/generate.ts`.
- `packages/server`: обработчик `/api/generate`, промпт и провайдеры вместе с записанными
  фикстурами.
- `packages/shared`: то, о чём клиент и сервер должны договориться: схема запроса, парсер
  event-stream и декодер Variant.

Vite, Vitest и тайпчекер читают TypeScript-исходники пакетов через export conditions
`development` и `types`. Node получает собранный `dist/`, потому что Vercel запускает функцию как
обычный Node ESM.

**Структура веб-приложения.** `apps/web/src` разделён по ролям, и к каждой папке ведёт алиас вроде
`@components/…`, объявленный один раз в `apps/web/tsconfig.app.json`:

- `app`: оболочка, то есть роуты, лэйаут, шапка и error boundary, со своими `components/` и
  `hooks/`.
- `pages`: по папке на страницу. Файл страницы только компонует. То, что нужно только этой
  странице, лежит рядом в `components/`, `hooks/` и, у генератора, `session/`.
- `components`, `hooks`: общие UI и хуки.
- `services`: очередь и клиент генерации, стор писем и его репозитории, профиль; обычный
  TypeScript без React.
- `providers`: контексты, которые передают сервисы в React.
- `utils`: браузерные детали вроде touch-only экранов, перемещения фокуса и буфера обмена, плюс
  хелпер для редьюсеров.

Компоненты тонкие: данные и действия приходят из хуков, а всё, что вычисляет, отслеживает или
отсчитывает время, живёт в хуке или в чистой функции рядом. Компонент с несколькими состояниями
рендерит по маленькому компоненту на состояние, а выбирает его чистая функция. Самый большой
случай — генератор: `GeneratorSession` (`pages/GeneratorPage/session/`) держит состояние страницы
в zustand-сторе, а её действия в методах, и контекст передаёт его вниз. Форма, кнопка и каждое
состояние превью выбирают нужное через маленькие хуки вместо десятка пропсов. То, что трогает DOM,
остаётся в компоненте, которому принадлежит узел: сессия кладёт в состояние запрос на фокус или
прокрутку, а форма или превью выполняют его после рендера. Редьюсеры — по маленькому переходу на
событие (`utils/reducer.ts`). Состояние со своим жизненным циклом — очередь, сессия генератора,
SSE-парсер, сохранённые поля формы, учёт фокуса на дашборде — это классы. Модуль держит внутри не
больше одного простого типа; остальные уходят в `types.ts` рядом.

React Compiler мемоизирует компоненты и хуки, поэтому `useMemo` и `useCallback` вручную нет. Он
работает через Babel 7: Babel 8 его пока ломает. Компилятор ещё и проверяет правила, на которые
опирается, например что реф не читается во время рендера: хук, которому нужен DOM-узел, получает
реф (с именем `…Ref`) от компонента, который этот узел рендерит.

**Прокси.** Браузер никогда не обращается к Generation API напрямую. Он отправляет четыре поля
формы на `/api/generate` (`apps/web/api/generate.ts` → `packages/server/src/generate.ts`), а тот
проверяет их той же zod-схемой, что и форма перед Generate (`packages/shared/src/generation.ts`;
`zod/mini`, потому что схема уходит и в браузер), собирает промпт на сервере
(`packages/server/src/prompt.ts`) и отдаёт тело ответа апстрима байт в байт. Токен остаётся на
сервере, а клиенты присылают поля формы, не промпт: системный промпт и лимит в 900 токенов
зафиксированы там. Переносы строк в однострочных полях отклоняются, чтобы поле не могло добавить
строку в системный промпт. Из ответа апстрима пробрасываются только `Content-Type`, `Retry-After`
и `X-Request-Id`. Отмена письма или закрытие вкладки отменяет запрос к апстриму
(`supportsCancellation` в `apps/web/vercel.json`, `request.signal` передаётся дальше).

Каждая генерация пишет одну JSON-строку в лог функции: провайдер, статус, ожидание заголовков
апстрима, длины навыков и деталей и id запроса апстрима. Запрос, брошенный браузером посреди
потока, добавляет строку `generate_cancelled`; брошенный до ответа апстрима попадает в лог
строкой `generate` со статусом 499. Текст полей не логируется никогда. Эти строки читает
`vercel logs`, и сегодня это единственный серверный сигнал для воронки конверсии.

Кросс-доменные запросы получают 403, чтобы страница с другого домена не могла вычерпать
единственный общий ключ через браузеры своих посетителей. Проверка сравнивает `Sec-Fetch-Site` и
`Origin` с `Host`: браузеры всегда шлют их на POST, а curl проходит. Это гигиена от CSRF, а не
аутентификация: пользователей у приложения нет. Настоящий провайдер отвечает 504, если апстрим не
прислал заголовков за 20 с. Таймер снимается, как только пошло тело, так что медленную модель
посреди письма не обрывают, но модель, которая так и не начала, функцию не вешает.

**Провайдеры.** В `packages/server/src/providers/` их два: `variant` (настоящий API) и `mock`.
`resolveProvider` выбирает провайдера на каждый запрос по окружению, по правилам из «Запуска
локально». Оба получают проверенный запрос и входящие заголовки и возвращают стандартный
`Response`, так что обработчик не знает, с каким из них говорит.

Мок выбирает транскрипт по длине деталей (short, medium, long), подменяет записанные должность и
компанию на те, что в запросе, и перенарезает текст на записанные размеры дельт, чтобы темп
оставался настоящим. Запросы, с которыми записаны транскрипты (`packages/server/src/samples.ts`),
общие с `record:fixture`, так что рекордер и мок не могут разойтись. Рекордер ничего не пишет, если
в транскрипте нет дословно должности и компании образца: иначе мок не смог бы вписать туда вашу
вакансию. Короткий образец — это запрос самого Try an example (`packages/shared/src/example.ts`),
поэтому без сети пример получает письмо, написанное под свои данные.

**Пайплайн стриминга.** `apps/web/src/services/generation/generationClient.ts` пропускает тело
ответа через web streams: сторож простоя на сырых байтах, `TextDecoderStream`, парсер event-stream
и декодер Variant. Оба последних лежат в общем пакете, ими же пользуются мок и рекордер фикстур.
Клиент читает события с конца пайплайна одним плоским циклом и отдаёт текст как async iterable. На
этой границе он остаётся генератором, потому что Safari до 26 не умеет итерировать поток. Тридцать
секунд без единого байта завершают запуск ошибкой вместо вечного спиннера; keepalive-комментарии
считаются признаком жизни. После `[DONE]` клиент до 2 с дочитывает соединение, чтобы браузер
записал запрос как завершённый, а не прерванный. Любой выход отменяет тело через его собственный
reader, потому что Safari держит соединение открытым, если отменить только pipe из тела
(`streams.ts`). Очередь генерации (`queue.ts`) собирает дельты в одно обновление за кадр анимации
и сбрасывает их перед финальным состоянием, так что хвост не теряется. Состояние каждого письма
проходит через редьюсер из переходов по событиям (`generationReducer.ts`). Очередь и стор писем
приложение получает через `AppProviders`: так тесты и Storybook подставляют фейковый клиент без
моков модулей.

**Очередь.** Письма пишет очередь уровня приложения, а не страница генератора. Поэтому письмо
продолжает писаться, когда вы вернулись в Applications (там оно видно карточкой), и тем временем
можно запросить следующие. Они идут по одному, и причина только в том, что у всех посетителей
один ключ Generation API с лимитом: параллельно несколько писем одного человека упёрлись бы в 429.
Без этого лимита я бы запускал их параллельно с ограничением на число одновременных. 429 держит
очередь, пока не пройдёт `Retry-After`; отсутствие сети тоже. Очередь живёт во вкладке, поэтому
«по одному» действует в пределах вкладки, а закрытие вкладки, пока письмо в пути, сначала
спрашивает подтверждение (собственный диалог браузера; телефоны могут его не показать).

**Состояние.** Письма живут в zustand-сторе (`apps/web/src/services/letters/store.ts`) поверх
асинхронного `LetterRepository`: `localStorageRepository.ts` в приложении, `inMemoryRepository.ts`
в тестах. Общий набор контрактных тестов гоняется на обоих. Стор создаётся уже загруженным, до
первого рендера, поэтому дашборд никогда не мелькает пустым состоянием. Стор сначала обновляет
память, потом сохраняет; неудачная запись оставляет письмо на экране и показывает пометку. События
`storage` синхронизируют вкладки. Письма лежат в версионированной обёртке: вкладка, которая нашла
более новую версию, не читает письма и отказывается писать, чтобы старая вкладка, открытая после
деплоя, не могла их затереть. Письмо в процессе написания — это состояние очереди. В стор оно
попадает один раз, когда поток завершён, со временем запроса, чтобы карточка сохранила своё
место. Try Again пишет под тем же id, и стор сохраняет исходный `createdAt`, так что карточка
остаётся на месте, а не прыгает наверх. Удаление письма отменяет его новую версию, если та ещё в
пути.

Поля формы переживают перезагрузку. Должность и компания — это черновик вкладки в
`sessionStorage` (`apps/web/src/pages/GeneratorPage/session/draft.ts`), помеченный письмом,
которому его передали, и забытый, как только письмо сохранено. Возврат в генератор, пока письмо
ещё пишется, начинается с пустой формы; после сбоя или перезагрузки вакансия возвращается. Навыки,
детали и имя для подписи — это профиль, zustand-стор поверх `localStorage`
(`apps/web/src/services/profile/profileStore.ts`). Он переходит на следующее письмо и следит за
событиями `storage`, так что имя, заданное в одной вкладке, подписывает карточки в другой.
Страница, которая профиль только читает, как дашборд, никогда его не пишет. Try an example
передаёт свой запрос в history state, который страница очищает после первого рендера. Его навыки
и детали попадают в черновик вкладки вместе с вакансией и никогда не попадают в профиль, пока вы
их не отредактируете.

**Роутинг.** react-router в декларативном режиме (`apps/web/src/app/App.tsx`): layout-роут
рендерит оболочку один раз, внутри неё `/`, `/new` и страница «не найдено». Error boundary стоит
внутри оболочки, так что упавшая страница сохраняет шапку и дорогу домой. При навигации приложение
прокручивает страницу наверх и переводит фокус на h1. Вкладка называется по этому h1: `PageTitle`
рендерит с ним `<title>` из React 19. TanStack Router я рассматривал и отказался: при одном бандле
и без лоадеров предзагружать нечего, а его типизированным параметрам и search-схемам здесь негде
пригодиться.

**Стили.** CSS Modules и custom properties, без CSS-in-JS и utility-фреймворков.
`apps/web/src/styles/index.css` — единственная глобальная точка входа: шрифты, семантические
токены, затем reset и базовые правила в cascade layers, чтобы любой модуль компонента их
перебивал. Компоненты делят `typography.module.css` (по классу на текстовую роль) и модули
контролов и утилит. Варианты — это классы CSS-модулей, которые выбирает class-variance-authority,
а не строки, собранные вручную. Состояния используют уже существующие атрибуты и псевдоклассы
(`:disabled`, `[aria-disabled]`, `[aria-busy]`, `[aria-invalid]`, `:read-only`, `[data-writing]`).
Брейкпоинты, которые зависят от места, доставшегося раскладке, — это container queries на колонке
страницы (генератор складывается в одну колонку уже 1120px). То, что относится к экрану, вроде
отступов и правил для телефонов, — viewport queries. Имена классов типизированы: `vite-css-modules`
пишет `.d.ts` рядом с каждым модулем (они в gitignore и генерируются перед каждой проверкой типов),
так что несуществующий класс роняет `tsc`.

**Заголовки.** `apps/web/vercel.json` отдаёт Content-Security-Policy `'self'` для всех источников,
с `frame-ancestors 'none'` и `object-src 'none'`. В сборке нет инлайновых скриптов и стилей,
поэтому nonce не нужен. Вместе с CSP идут `X-Content-Type-Options`, `Referrer-Policy` и
`Permissions-Policy`, которая выключает камеру, микрофон и геолокацию. Всё под `/assets/` имеет
хэш в имени файла, поэтому кэшируется как immutable на год. SPA-rewrite пропускает `/assets/`, так
что отсутствующий файл с хэшем даёт 404, а не оболочку приложения, закэшированную под
immutable-адресом. `pnpm dev` ничего из этого не выставляет.

## Особенности Generation API

Чем живой API отличается от опубликованной спецификации:

- Поток обычно начинается с комментария `: keepalive`, если первый токен ещё не готов; если
  готов, первая строка уже событие.
- Он заканчивается голой строкой `data: [DONE]`, хотя спецификация говорит, что терминатора нет.
- Иногда он обрывает письмо на полуслове и всё равно чисто закрывает поток, с `[DONE]` или без
  (3 из примерно 43 живых писем). Ни одно событие не сообщает причину завершения, так что по
  одному потоку нельзя отличить целое письмо от обрезанного.
- CORS открыт. Проксирую всё равно: ради токена и промпта.

Как клиент решает, что поток закончился. `[DONE]` или чистое закрытие считаются **завершением**,
только если текст заканчивается как письмо: на прощании (промпт просит «Sincerely,»), на имени под
ним или хотя бы на законченном предложении (`looksWhole` в
`apps/web/src/services/letters/model.ts`). Все живые обрывы останавливались на полуслове, а целое
письмо, принятое за обрезанное, падало бы так же на каждом повторе, поэтому проверка склоняется к
«целому». Письмо, которое остановилось на полуслове, или соединение, которое рвётся или молчит 30 с
после прихода текста, считается **обрезанным**: текст остаётся, ничего не сохраняется,
предлагается Try Again. Если не пришло вообще ничего, это сбой. 429 показывает обратный отсчёт из
`Retry-After`. Try Again, как и любой запуск поверх готового письма, если он обрезан или упал,
оставляет сохранённое письмо на экране с пометкой над ним; пометка называет вакансию письма, если
с тех пор её изменили. Парсер, декодер и клиент проверены на записанных фикстурах, включая один и
тот же транскрипт, разрезанный на каждом байте.

Формат протокола живёт в одном модуле, `packages/shared/src/variantDecoder.ts`: клиент им
декодирует, а мок и рекордер фикстур им кодируют и парсят, так что изменение формата — одна
правка. Эндпоинт и авторизация — в `packages/server/src/providers/variant.ts`.

Промпт фиксирует приветствие («Dear {Company} team,») и прощание, под которым встаёт подпись.
Начало письма получилось с четвёртой попытки. Все три первые записи начинались с «I am writing to
express my interest» или «I am excited to apply». После запрета этих фраз каждое письмо начиналось
со стажа. Требование назвать роль в первом предложении привело к тому, что каждое письмо
открывалось «As a {role}». Просьба привести конкретный пример, когда в деталях его не было,
заставила модель его выдумать («a 40% increase in loading speed»). Теперь промпт открывает первый
абзац самым сильным примером, который реально есть в деталях, называет роль дальше в этом абзаце,
не просит никаких результатов, если детали пустые, и требует, чтобы каждое число бралось из ввода.
Каждую версию я прогонял на шести запросах к живому API, включая один без деталей и один без
стажа, и перезаписал фикстуры последней. На скудном вводе модель всё равно добавляет воду. Короткая
фикстура, записанная по запросу Try an example (HTML, CSS, соблюдение сроков и два предложения
пожеланий), не называет ни чисел, ни результатов, но добавляет работу, которой никто не давал
(«cross-functional teams», «from concept to launch»), и льстит компании («Apple's commitment to
innovation and excellence»). Средняя держится фактов, но добавляет один собственный результат
(«ensuring consistency across products»). Более жёсткий нажим на начало письма давал выдуманные
результаты, а это хуже.

## Дизайн-решения

**Макеты.** В файле Figma девять десктопных фреймов, но нет ни переменных, ни стилей, ни
компонентов: каждая «Button» — отвязанный фрейм. Имена токенов и границы компонентов мои, выведены
из повторяющейся структуры, а все значения — точные литералы из файла. Анимация загрузки
восстановлена по двум статичным полюсам. Расхождения между фреймами (скругление поля 8 и 6, кнопка
загрузки высотой 56 против 60, «4/5» в шапке при трёх полосках на баннере и другие) сведены к
одному решению для каждого. Figma рисует обводку внутри бокса, поэтому у элементов с рамкой
отступы на 1px меньше, чем в макете.

**Пустой дашборд.** Заголовок и баннер «0 out of 5» остаются, а вместо сетки стоит панель в стиле
превью. Она объясняет продукт одной фразой и даёт одно действие, Try an example, с короткой
пометкой: регистрация не нужна, данные уходят в сервис генерации только чтобы написать письмо,
письма остаются в браузере. Try an example открывает генератор с запросом из макетов; навыки и
детали примера не сохраняются как ваши.

**Планшет и телефон.** Когда колонке страницы меньше 1120px, генератор складывается: форма, под ней
превью, которое на старте генерации само прокручивается в зону видимости. Меньше 656px дашборд
переходит в одну колонку, карточки остаются высотой 240px. На телефонах должность и компания встают
друг под друга, заголовок переносится вместо многоточия, а шапка ужимает логотип, но не кнопку
Home. На touch-only устройствах генератор не ставит курсор в первое поле, чтобы не открывать
клавиатуру поверх страницы.

**Стриминг.** Та же типографика и раскладка, что у готового письма, так что в конце ничего не
перестраивается. Текст добавляется по мере прихода, без эффекта печатной машинки. Пока письмо
пишется, на верхнем крае панели висит чип «Writing…» с пульсирующей точкой, а по фону проходит
мягкая светлая полоса. После 3 с без нового текста чип говорит «Still writing…». Пока не пришёл
первый токен, под орбом через 2 с появляется «Writing your letter for {Company}…», а через 8 с
«Almost there…». Скринридер не читает письмо по мере написания: объявляются только старт,
готовность и обрыв.

**Ошибки.** Показываются внутри превью, нейтральными цветами. 429 — «Too many requests» с кнопкой
«Retry in {n}s», которая отсчитывает время. Ошибки 401, 403, 5xx, 504 прокси и поток, оборвавшийся
до текста, — «Generation failed» с Retry. Нет сети — «You appear to be offline», и Retry ждёт
возвращения сети. Обрыв посреди письма оставляет текст с пометкой «The letter was cut short.» и
Try Again. Неудачная повторная генерация никогда не отнимает уже сохранённое письмо: оно остаётся на
экране с Copy и пометкой над ним.

**Карточки и очередь.** Письмо, которое не влезает в карточку, получает Read more поверх последней,
затухающей строки. Кнопка открывает письмо целиком в диалоге с Close и Copy, страница под ним не
прокручивается. Письма в пути — это карточки в том же списке: «Queued» с тем, чего они ждут, потом
«Writing…» с растущим текстом и Cancel. Сохранённое письмо становится обычной карточкой на том же
месте. После Delete или Cancel фокус переходит на следующую карточку или на заголовок страницы.

**Правила продукта.** Счётчик — это число писем, которые у вас есть: он вычисляется, а не
хранится, и удаление ниже пяти возвращает баннер. Пять — цель, а не лимит. Один визит в генератор —
одно письмо-кандидат: Try Again заменяет его на месте, а правка любого поля делает следующий
запуск новым письмом. Кнопки генерации никогда не бывают `disabled`, только `aria-disabled`, чтобы
фокус не терялся; нажатие на неактивную кнопку говорит, чего не хватает. Имя для подписи вводится
один раз, хранится в профиле и встаёт под прощание в каждом письме.

## Конверсия

Конверсия здесь — посетитель, который пришёл, сгенерировал письмо, скопировал его и вернулся за
следующими четырьмя. Воронка: приход → генератор → валидная форма → генерация → готовое письмо →
копирование → письма 2–5. Аккаунтов и аналитики нет, поэтому метрики определены, но не
собираются; единственный серверный сигнал сегодня — JSON-строка в логе прокси.

Что уже сделано для неё:

- Try an example: первое письмо без ввода.
- Generate Now, который называет, чего не хватает, и ставит туда курсор.
- Подписи во время ожидания и стриминга; восстановление без перезагрузки: отсчёт после 429,
  Try Again под обрезанным письмом, сохранённое письмо при неудачном повторе.
- Промпт без шаблонных зачинов, которому запрещено выдумывать числа и результаты.
- Подпись и профиль: письма 2–5 стоят только должности и компании. «Same role, another company»
  после копирования: следующее письмо стоит только названия компании.
- Очередь, которая дописывает письмо, пока вы начинаете следующее.
- Вакансия в заголовке вкладки, чтобы нужную вкладку было легко найти.

Что я бы делал дальше, в порядке ожидаемого эффекта: редактирование письма перед копированием;
«Same role, another company» прямо с карточки; типизированный слой событий для воронки, без текста
полей; deep links вида `/new?jobTitle=…&company=…`; продолжение незаконченного отклика с дашборда.

инстанцированный под веса типографической шкалы (wght 400–600; wdth оставлен 87.5–100) и урезанный
до Latin, Latin Extended-A, Cyrillic, General Punctuation, € и ™ с сохранением `kern`, `liga` и
`tnum`: 71 КБ вместо 148 КБ. Кириллица оставлена, потому что форма её принимает.

```sh
uvx --from 'fonttools[woff]' fonttools varLib.instancer FixelVariable.ttf wght=400:600 -o instanced.ttf
# В исходнике maxp.maxZones = 0, и санитайзер шрифтов Firefox (OTS) ругается на это при каждой загрузке.
uvx --from 'fonttools[woff]' python -c "from fontTools.ttLib import TTFont; f=TTFont('instanced.ttf'); f['maxp'].maxZones=1; f.save('instanced.ttf')"
uvx --from 'fonttools[woff]' pyftsubset instanced.ttf \
  --unicodes="U+0000-00FF,U+0100-017F,U+0400-04FF,U+2000-206F,U+20AC,U+2122" \
  --layout-features="kern,liga,tnum" --flavor=woff2 \
  --output-file=apps/web/src/assets/fonts/FixelVariable.woff2
```

Один файл обслуживает оба семейства: Fixel Text (ось ширины 87.5) и Fixel Display (ширина 100).
