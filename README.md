# Alt+Shift

**Демо:** https://alt-shift-ochre.vercel.app

## Запуск локально

Node 24 (`.node-version`), pnpm 10 (закреплён в `packageManager`) и TypeScript 7. Код везде нацелен на ES2025. Полифилов нет, поэтому сборка для браузера нацелена на первые версии, где есть весь ES2025: Chrome и Edge 136, Firefox 138, Safari 18.4 (весна 2025).

```sh
pnpm i && pnpm dev
```

Ни аккаунтов, ни ключей не нужно. Без токена API-роут работает на **mock-провайдере**: он проигрывает настоящие ответы API, записанные в `packages/server/fixtures/`, в реалистичном темпе и вписывает в письмо вашу должность и компанию. Сценарии сбоев включаются заголовком запроса `x-mock-scenario`: `disconnect` (поток обрывается посередине), `truncate` (закрывается чисто, но на полуслове и без `[DONE]`, как иногда делает живой API), `rate-limit`, `upstream-error`, `invalid-token` (любое другое значение даёт 400).

Чтобы работать с настоящим Generation API, скопируйте `.env.example` в `.env.local` в корне репозитория и задайте `GENERATION_API_TOKEN`. Дев-сервер при старте пишет, какой провайдер активен. Деплои (задан `VERCEL_ENV`) всегда используют настоящий API и без токена не стартуют.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `GENERATION_API_TOKEN` | — | Задан: настоящий API. Пустой: мок |
| `GENERATION_PROVIDER` | — | `variant` или `mock` выбирает провайдера локально принудительно; любое другое значение останавливает дев-сервер; на деплоях игнорируется |
| `GENERATION_API_URL` | эндпоинт Variant | Куда отправляет запросы настоящий провайдер |
| `GENERATION_FIRST_BYTE_TIMEOUT_MS` | `20000` | Сколько настоящий провайдер ждёт заголовков апстрима, прежде чем ответить 504 |
| `MOCK_FIRST_DELTA_MS` / `MOCK_DELAY_MS` | `1200` / `40` | Темп мока: до первой дельты, затем между дельтами |

`pnpm dev` обслуживает API-роут через небольшой плагин Vite, который монтирует тот же обработчик,
что экспортирует функция Vercel. `vercel dev` тоже подходит для сверки с продакшеном, но ему нужны
привязанный проект и токен: он задаёт `VERCEL_ENV`, поэтому всегда ходит в настоящий API.

На Vercel Root Directory проекта — `apps/web`. `apps/web/vercel.json` запускает сборку через
Turborepo из корня репозитория, чтобы пакеты, которые импортирует функция, собирались первыми.

## Скрипты

| Скрипт | Что делает |
|---|---|
| `dev` | Дев-сервер Vite с `/api/generate` |
| `build` | Собирает пакеты в `dist/`, затем проверяет типы и собирает веб-приложение |
| `typecheck` | `tsc` во всех пакетах; у серверного и общего кода нет DOM-библиотеки, так что браузерные глобалы им недоступны. Веб-приложение сначала генерирует типы CSS-модулей |
| `lint` / `format` / `check` | Biome по всему репозиторию |
| `test` / `test:coverage` | Vitest во всех пакетах: server и shared в Node, веб-приложение в jsdom |
| `test:e2e` | Playwright против mock-провайдера на порту 4173, в 1440×900 и 360×800 (самая частая ширина Android) |
| `storybook` / `build-storybook` | Каталог компонентов и страниц |
| `record:fixture <short\|medium\|long>` | Записывает настоящий ответ API в `packages/server/fixtures/` (нужен `.env.local`; стоит одного запроса) |

Из корня репозитория скрипты идут через Turborepo, который кэширует результаты каждого пакета.

CI (`.github/workflows/ci.yml`) на пушах в `main` и на pull request'ах гоняет typecheck, Biome
check (линт, формат и порядок импортов), покрытие, сборку и e2e.

## Архитектура

**Раскладка.** pnpm workspace под управлением Turborepo:

- `apps/web`: SPA на Vite, Storybook и e2e-тесты, а также вход функции Vercel `api/generate.ts`.
- `packages/server`: обработчик `/api/generate`, промпт и провайдеры вместе с записанными фикстурами.
- `packages/shared`: контракт клиента и серверва: схема запроса, парсер event-stream и декодер Variant.

Vite, Vitest и тайпчекер читают TypeScript-исходники пакетов через export conditions `development` и `types`. Node получает собранный `dist/`, потому что Vercel запускает функцию как обычный Node ESM.

**Структура веб-приложения.** `apps/web/src` разделён по ролям, и к каждой папке ведёт алиас вроде
`@components/…`, объявленный один раз в `apps/web/tsconfig.app.json`:

- `app`: оболочка, то есть роуты, лэйаут, шапка и error boundary, со своими `components/` и `hooks/`.
- `pages`: по папке на страницу. Файл страницы только компонует. То, что нужно только этой странице,  лежит рядом в `components/`, `hooks/` и, у генератора, `session/`.
- `components`, `hooks`: общие UI и хуки.
- `services`: очередь и клиент генерации, стор писем и его репозитории, профиль; обычный TypeScript без React.
- `providers`: контексты, которые передают сервисы в React.
- `utils`: браузерные детали вроде touch-only экранов, перемещения фокуса и буфера обмена, плюс
  хелпер для редьюсеров.

Компоненты тонкие: данные и действия приходят из хуков, а всё, что вычисляет, отслеживает или отсчитывает время, живёт в хуке или в pure функции рядом. Компонент с несколькими состояниями рендерит по маленькому компоненту на состояние, а выбирает его чистая функция. 
Самый большой участок - генератор: `GeneratorSession` (`pages/GeneratorPage/session/`) держит состояние страницы в zustand-сторе, а её действия в методах, и контекст передаёт его вниз. Форма, кнопка и каждое состояние превью выбирают нужное через маленькие хуки вместо десятка пропсов. То, что касается DOM, остаётся в компоненте, которому принадлежит узел: сессия кладёт в состояние запрос на фокус или прокрутку, а форма или превью выполняют его после рендера. Редьюсеры - по переходу на событие (`utils/reducer.ts`). 
Каждый модуль держит внутри не больше одного простого типа; остальные уходят в `types.ts` рядом.

**Прокси.** Браузер никогда не обращается к Generation API напрямую. Он отправляет четыре поля
формы на `/api/generate` (`apps/web/api/generate.ts` → `packages/server/src/generate.ts`), а тот
проверяет их той же zod-схемой, что и форма перед Generate (`packages/shared/src/generation.ts`;
`zod/mini`, потому что схема уходит и в браузер), собирает промпт на сервере (`packages/server/src/prompt.ts`) и отдаёт тело ответа апстрима байт в байт. Токен остаётся на сервере, а клиенты присылают поля формы, не промпт: системный промпт и лимит в 900 токенов зафиксированы там. Переносы строк в однострочных полях отклоняются, чтобы поле не могло добавить строку в системный промпт. Из ответа апстрима пробрасываются только `Content-Type`, `Retry-After` и `X-Request-Id`. Отмена письма или закрытие вкладки отменяет запрос к апстриму (`supportsCancellation` в `apps/web/vercel.json`, `request.signal` передаётся дальше).

Каждая генерация пишет одну JSON-строку в лог функции: провайдер, статус, ожидание заголовков апстрима, длины навыков и деталей и id запроса апстрима. Запрос, cброшенный браузером посреди потока, добавляет строку `generate_cancelled`; cброшенный до ответа апстрима попадает в лог строкой `generate` со статусом 499. Текст полей не логируется никогда. Эти строки читает `vercel logs`, и сегодня это единственный серверный сигнал для воронки конверсии.

Кросс-доменные запросы получают 403. Проверка сравнивает `Sec-Fetch-Site` и `Origin` с `Host`: браузеры всегда шлют их на POST, а curl проходит. Настоящий провайдер отвечает 504, если апстрим не прислал заголовков за 20 с. Таймер снимается, как только пошло тело, так что медленную модель посреди письма не обрывают, но модель, которая так и не начала, функцию не вешает.

**Провайдеры.** В `packages/server/src/providers/` их два: `variant` (настоящий API) и `mock`.
`resolveProvider` выбирает провайдера на каждый запрос. Оба получают проверенный запрос и входящие заголовки и возвращают стандартный `Response`, так что обработчик не знает, с каким из них говорит.

**Пайплайн стриминга.** `apps/web/src/services/generation/generationClient.ts` пропускает тело
ответа через web streams: сторож простоя на сырых байтах, `TextDecoderStream`, парсер event-stream
и декодер Variant. Оба последних лежат в общем пакете, ими же пользуются мок и рекордер фикстур.
Клиент читает события с конца пайплайна одним плоским циклом и отдаёт текст как async iterable. На
этой границе он остаётся генератором, потому что Safari до 26 не умеет итерировать поток. Тридцать
секунд без единого байта завершают запуск ошибкой вместо вечного спиннера; keepalive-комментарии
считаются признаком жизни. После `[DONE]` клиент до 2 с дочитывает соединение, чтобы браузер
записал запрос как завершённый, а не прерванный. Любой выход отменяет тело через его собственный
reader, потому что Safari держит соединение открытым, если отменить только pipe из тела
(`streams.ts`). Очередь генерации (`queue.ts`) собирает дельты в одно обновление за кадр анимации
и сбрасывает их перед финальным состоянием, так что хвост не теряется. Состояние каждого письма
проходит через редьюсер из переходов по событиям (`generationReducer.ts`). Очередь и стор писем
приложение получает через `AppProviders`: так тесты и Storybook подставляют фейковый клиент без
моков модулей.

**Очередь.** Письма пишет очередь на уровне всего приложения, а не страницы. Поэтому письмо
продолжает генерироваться, если пользователь вернется в дашборд. 
Генерация не идет параллельно только из-за жесткого лимита Generation API, чтобы не упираться часто в лимит.
Без этого лимита я бы запускал их параллельно с ограничением на число одновременных. 429 держит очередь, пока не пройдёт `Retry-After`; отсутствие сети тоже. Очередь живёт во вкладке, поэтому «по одному» действует в пределах вкладки, а закрытие вкладки, пока письмо в пути, сначала спрашивает подтверждение.

**Состояние.** Письма живут в zustand-сторе (`apps/web/src/services/letters/store.ts`) поверх асинхронного `LetterRepository`: `localStorageRepository.ts` в приложении, `inMemoryRepository.ts` в тестах. Общий набор контрактных тестов гоняется на обоих. Стор создаётся уже загруженным, до первого рендера, поэтому дашборд никогда не мелькает пустым состоянием. Стор сначала обновляет память, потом сохраняет; неудачная запись оставляет письмо на экране и показывает пометку. События `storage` синхронизируют вкладки. Письма лежат в версионированной обёртке: вкладка, которая нашла более новую версию, не читает письма и отказывается писать, чтобы старая вкладка, открытая после деплоя, не могла их затереть. Письмо в процессе написания - это состояние очереди. В стор оно попадает один раз, когда поток завершён, со временем запроса, чтобы карточка сохранила своё место. Try Again пишет под тем же id, и стор сохраняет исходный `createdAt`, так что карточка остаётся на месте, а не прыгает наверх. Удаление письма отменяет его новую версию, если та ещё в пути.

Поля формы переживают перезагрузку. Должность и компания - это черновик вкладки в `sessionStorage` (`apps/web/src/pages/GeneratorPage/session/draft.ts`), помеченный письмом, которому его передали, и забытый, как только письмо сохранено. Возврат в генератор, пока письмо ещё пишется, начинается с пустой формы; после сбоя или перезагрузки вакансия возвращается. 
Навыки, детали и имя для подписи - это профиль пользователя, zustand-стор поверх `localStorage` (`apps/web/src/services/profile/profileStore.ts`). Он переходит на следующее письмо и следит за событиями `storage`, так что имя, заданное в одной вкладке, подписывает карточки в другой. Страница, которая профиль только читает, как дашборд, никогда его не пишет. Try an example передаёт свой запрос в history state, который страница очищает после первого рендера. Его навыки
и детали попадают в черновик вкладки вместе с вакансией и никогда не попадают в профиль, пока вы их не отредактируете.

**Роутинг.** react-router в декларативном режиме (`apps/web/src/app/App.tsx`): layout-роут рендерит оболочку один раз, внутри неё `/`, `/new` и страница «не найдено». Error boundary стоит внутри оболочки, так что упавшая страница сохраняет шапку. При навигации приложение прокручивает страницу наверх и переводит фокус на h1. Вкладка называется по этому h1: `PageTitle` рендерит с ним `<title>` из React 19. 
Я рассматривал TanStack Router в качестве альтернативы, но отказался, потому что в текущем состоянии приложения, все фичи TanStack не нужны.

**Стили.** CSS Modules и custom properties, без CSS-in-JS и utility-фреймворков. `apps/web/src/styles/index.css` — единственная глобальная точка входа: шрифты, семантические токены, затем reset и базовые правила в cascade layers, чтобы любой модуль компонента их перебивал. Компоненты делят `typography.module.css` (по классу на текстовую роль) и модули контролов и утилит. Варианты - это классы CSS-модулей, которые собираются с помощью `class-variance-authority`. Состояния используют уже существующие атрибуты и псевдоклассы (`:disabled`, `[aria-disabled]`, `[aria-busy]`, `[aria-invalid]`, `:read-only`, `[data-writing]`).
Брейкпоинты, которые зависят от места, доставшегося раскладке, - это container queries на колонке страницы (генератор складывается в одну колонку уже 1120px). То, что относится к экрану, вроде отступов и правил для телефонов, — viewport queries. Имена классов типизированы: `vite-css-modules` пишет `.d.ts` рядом с каждым модулем (они в gitignore и генерируются перед каждой проверкой типов), так что несуществующий класс должен уронить `tsc`.

**Заголовки.** `apps/web/vercel.json` отдаёт Content-Security-Policy `'self'` для всех источников, с `frame-ancestors 'none'` и `object-src 'none'`. В сборке нет инлайновых скриптов и стилей, поэтому nonce не нужен. Вместе с CSP идут `X-Content-Type-Options`, `Referrer-Policy` и `Permissions-Policy`, которая выключает камеру, микрофон и геолокацию. Всё под `/assets/` имеет хэш в имени файла, поэтому кэшируется как immutable на год. SPA-rewrite пропускает `/assets/`, так что отсутствующий файл с хэшем даёт 404, а не оболочку приложения, закэшированную под immutable-адресом. `pnpm dev` ничего из этого не выставляет.

## Особенности Generation API

**Как понять, что письмо дописано.** API не сообщает, закончила модель письмо или оборвалась на полуслове, а обрывы на живом API случались. Поэтому клиент смотрит на сам текст (`looksWhole` в `apps/web/src/services/letters/model.ts`). Письмо считается готовым, если оно кончается прощанием (промпт просит «Sincerely,»), именем под ним или хотя бы законченным предложением.

Письмо считается обрезанным в трёх случаях: текст оборвался на полуслове, соединение порвалось или 30 секунд не приходит ничего нового. Тогда текст остаётся на экране, в список ничего не сохраняется, и можно нажать Try Again. В спорных случаях проверка скорее примет письмо за целое. Все настоящие обрывы были на полуслове, а целое письмо, ошибочно принятое за обрезанное, «обрывалось» бы на каждом повторе.

Разбор потока проверен на записанных ответах API, в том числе когда один и тот же ответ разрезан на каждом байте. Формат ответа описан в одном модуле, `packages/shared/src/variantDecoder.ts`. Адрес API и авторизация - в `packages/server/src/providers/variant.ts`.

**Промпт.** Приветствие («Dear {Company} team,») и прощание в промпте зафиксированы, подпись встаёт под прощанием. Нормальное начало письма получилось только с четвёртой попытки:

1. Первые письма начинались с шаблонов «I am writing to express my interest» и «I am excited to apply».
2. Когда я их запретил, все письма стали начинаться со стажа.
3. Когда потребовал назвать роль в первом предложении, все начинались с «As a {role}».
4. Когда попросил конкретный пример, модель выдумывала его, если в деталях примера не было (например, «a 40% increase in loading speed»).

Сейчас промпт начинает письмо с самого сильного примера из деталей пользователя и называет роль дальше в первом абзаце. Если детали пустые, он не просит никаких результатов, и цифры, которых нет во вводе, ему запрещены. Каждую версию я проверял на шести запросах к живому API, а в конце перезаписал фикстуры.
На скудных данных модель всё равно добавляет воду: приписывает работу, о которой никто не говорил («cross-functional teams»), и льстит компании. Попытки дожать промпт сильнее приводили к выдуманным результатам, поэтому остановился на том, что есть.

В целом, основные критерии для полировки промпта были:
1. Письмо не должно звучать как шаблон.
2. Модель не должна выдумывать факты.
3. Нужна предсказуемая структура письма.

## Дизайн-решения

**Макеты.** В Figma нет готовой дизайн-системы: ни переменных, ни стилей, ни компонентов. Токены и компоненты я собрал сам по тому, что повторяется в макетах, а значения взял из файла как есть. Где фреймы расходятся друг с другом (разные скругления, высота кнопки, счётчик писем), выбрал один вариант на свой вкус.

**Пустой дашборд.** Это мое дополнение к макетам. Новый пользователь попадает на пустую страницу и не понимает, что это за продукт. Поэтому вместо пустой сетки стоит панель, которая одной фразой объясняет, что делает Alt+Shift. Главное действие на ней **Try an example(()): генератор открывается уже заполненным, и первое письмо можно получить, ничего не вводя. Это самый быстрый способ увидеть, как работает продукт. Под кнопкой короткая пометка: регистрация не нужна, данные уходят только на генерацию письма, письма хранятся в браузере. Она снимает сомнение, стоит ли вводить о себе что-то личное. Навыки и детали из примера не сохраняются в профиль, чтобы следующее настоящее письмо не ушло с чужой биографией.

**Планшет и телефон.** Когда колонке страницы меньше 1120px, генератор складывается: форма, под ней превью, которое на старте генерации само прокручивается в зону видимости. Меньше 656px дашборд переходит в одну колонку, карточки остаются высотой 240px. На телефонах должность и компания встают друг под друга, заголовок переносится вместо многоточия, а шапка ужимает логотип, но не кнопку Home. На touch-only устройствах генератор не ставит курсор в первое поле, чтобы не открывать клавиатуру поверх страницы.

**Стриминг.** Та же типографика и раскладка, что у готового письма, так что в конце ничего не перестраивается. Текст добавляется по мере прихода, без эффекта печатной машинки. Пока письмо пишется, на верхнем крае панели висит чип «Writing…» с пульсирующей точкой, а по фону проходит мягкая светлая полоса. После 3с без нового текста чип говорит «Still writing…». Пока не пришёл первый токен, под орбом через 2 с появляется «Writing your letter for {Company}…», а через 8 с «Almost there…». Скринридер не читает письмо по мере написания: объявляются только старт, готовность и обрыв.

**Ошибки.** Показываются внутри превью, нейтральными цветами. 429 — «Too many requests» с кнопкой «Retry in {n}s», которая отсчитывает время. Ошибки 401, 403, 5xx, 504 прокси и поток, оборвавшийся до текста, — «Generation failed» с Retry. Нет сети — «You appear to be offline», и Retry ждёт возвращения сети. Обрыв посреди письма оставляет текст с пометкой «The letter was cut short.» и Try Again. Неудачная повторная генерация никогда не отнимает уже сохранённое письмо: оно остаётся на экране с Copy и пометкой над ним.

**Карточки и очередь.** Письмо, которое не влезает в карточку, получает Read more поверх последней, затухающей строки. Кнопка открывает письмо целиком в диалоге с Close и Copy, страница под ним не прокручивается. Письма в пути — это карточки в том же списке: «Queued» с тем, чего они ждут, потом «Writing…» с растущим текстом и Cancel. Сохранённое письмо становится обычной карточкой на том же месте. После Delete или Cancel фокус переходит на следующую карточку или на заголовок страницы.

**Правила продукта.** Счётчик - это число писем, которые у вас есть. Оно всегда вычисляется, а не хранится. Удаление ниже пяти возвращает баннер. Один визит в генератор - одно письмо-кандидат: Try Again заменяет его на месте, а правка любого поля делает следующий запуск новым письмом. Кнопки генерации никогда не бывают `disabled`, только `aria-disabled`, чтобы фокус не терялся; нажатие на неактивную кнопку говорит, чего не хватает. Имя для подписи вводится один раз, хранится в профиле и встаёт под прощание в каждом письме.

## Конверсия

Конверсия здесь - посетитель, который пришёл, сгенерировал письмо, скопировал его и вернулся за следующими четырьмя. Воронка: приход → генератор → валидная форма → генерация → готовое письмо → копирование → письма 2–5. Аккаунтов и аналитики нет, поэтому метрики определены, но не собираются.

Что уже сделано для неё:

- Try an example: первое письмо без ввода.
- Generate Now, который называет, чего не хватает, и ставит туда курсор.
- Подписи во время ожидания и стриминга; восстановление без перезагрузки: отсчёт после 429, Try Again под обрезанным письмом, сохранённое письмо при неудачном повторе.
- Промпт без шаблонных фраз, которому запрещено выдумывать числа и результаты.
- Подпись и профиль: письма 2–5 стоят только должности и компании. «Same role, another company» после копирования: следующее письмо требует только ввода названия компании.
- Очередь, которая дописывает письмо, пока вы начинаете следующее.
- Вакансия в заголовке вкладки, чтобы нужную вкладку было легко найти.

Что я бы делал дальше, в порядке ожидаемого эффекта: редактирование письма перед копированием; возможность добавить ссылку на job post, чтобы вытянуть дополнительный контекст; «Same role, another company» прямо с карточки; типизированный слой событий для воронки.

**Где я не согласился:**

- Состояние. Агент держал состояние страницы в хуках и в одном контексте, который раздавал десяток значений каждой части генератора. Я перенёс его в zustand-сторы (письма, очередь, профиль, сессия генератора), которые читаются через селекторы; контекст только передаёт экземпляры сторов, так что тесты и Storybook подставляют свои.
- Первая версия пересылала из браузера в API готовый промпт. Теперь промпт собирает сервер из полей формы.
- Валидация была написана вручную, причём дважды: в форме и на сервере. Теперь это одна zod-схема на `zod/mini`, потому что полный zod весил в бандле вчетверо больше.
- `src/`, `server/`, `shared/` и `api/` лежали рядом в одном пакете. Теперь это Turborepo workspace: приложение и два пакета.
- Сохранение письма в момент старта генерации заменено черновиком вкладки; письмо сохраняется, когда оно дописано.

**Код, который я считаю самым своим:** Наверно, самым "моим" будет очередь генерации (`apps/web/src/services/generation/queue.ts`).
